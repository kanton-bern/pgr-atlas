# Behaviour inventory

What a user can do in each view, what they put in, and what they see. It describes behaviour,
not implementation, so it stays valid when the code under a flow changes. Each flow names the
test that covers it, which makes this the map the tests are written against. How to run the
tests: [`tests/README.md`](../../tests/README.md).

**Test columns:**
- `c:` is `tests/components/` (one component in a local page, fake args).
- `e:` is `tests/e2e/` (the whole app in a browser, against the `adelboden-test` bucket).
- `a:` is `tests/apptest/` (`app.py` run in-process by Streamlit's AppTest, same bucket).
- `u:` is a Python unit test in `tests/`.
- `v:` is a Vitest test of the frontend, `frontend/src/<component>/<file>.test.ts` (`npm run test` in `frontend/`).
- **open** marks a flow without a test yet, with the reason.
- **xfail** marks a known bug. Its test is written as `xfail(strict=True)`, so the test fails
  loudly once the bug is fixed and the marker has to go.

## Shared map chrome (Simulierte Ereignisse, IFK-Berechnung, Raster-Karten (ad hoc), Raster-Derivate)

The chrome is one module (`frontend/src/shared/map-controls.ts`). Its behaviour is tested on
Simulierte Ereignisse. IFK (`overview_ifk`) and Raster-Karten/-Derivate (both
`raster_bbox_map`) get the "Map loads" smoke test; their own coordinate-search and "Zoom
Kanton Bern" callbacks have no browser test.
