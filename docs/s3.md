# S3 at Bedag and Hosttech

Where the app's data lives, how buckets are created, and how to
work with them (the s3-toolbox and `s3m`).
Full `s3m` reference: [tools/s3/README.md](../tools/s3/README.md).

---

## 1. Two object stores

| | Hosttech | Bedag |
|---|---|---|
| What | Ceph (Hosttech's object storage) | NetApp StorageGRID (`primary-grid`), one S3 tenant per stage |
| Endpoint | `https://f712.gos3.io` | `https://x7ba-s3-kakbfe.infra.be.ch:10443` (test **and** prod) |
| Region | `f712` (what every bucket reports as its location) | `ch-bern-1` |
| Reachable from | anywhere; from Bedag's clusters through the proxy `proxy.kb-bedag.ch:8080` | **only from pods inside Bedag's clusters** that a network policy lets through; from outside it times out |
| Role today | where the pipeline writes; read by local development and CI (`adelboden-test`, `maxi`). The app at Bedag has no Hosttech target, key or proxy; only the s3-toolbox reaches Hosttech from there, to copy new data | the only S3 the app at Bedag reads: `aw3-pgr-atlas-test` on test, `aw3-pgr-atlas-prod` on prod |

Region is only the name requests are signed with. Where the data lives is
decided by the endpoint.

## 2. Bedag: tenants, buckets, keys

| | test (`kb-common-test`) | prod (`kb-common-prod`) |
|---|---|---|
| Namespace | `aw3-pgr-atlas-test-apps` | `aw3-pgr-atlas-prod-apps` |
| S3Tenant | `aw3-pgr-atlas-s3-test`, [tenant.yaml](../deploy/stages/test/pgr-atlas/s3/tenant.yaml) | `aw3-pgr-atlas-s3-prod`, [tenant.yaml](../deploy/stages/prod/pgr-atlas/s3/tenant.yaml) |
| Tenant account ID | `21870741000991081934` | `33613919856226121421` |
| Quota | 1000 GiB | 20000 GiB |
| Buckets | `aw3-pgr-atlas-test` (Git), `aw3-pgr-atlas-test-archive` (Git, for archive data, not versioned), `adelboden-test` (created by Bedag by hand, **not** in Git, holds the copy of Hosttech's `adelboden-test`) | `aw3-pgr-atlas-prod` (Git; the copy of Hosttech's `maxi`), `aw3-pgr-atlas-prod-archive` (Git, for archive data) |
| Versioning | Enabled on both | Enabled |

**One grid, several tenants.** Test and prod use the same endpoint. The
**access key decides which tenant a request belongs to**, not the URL: the
test key sees only the test tenant's buckets, the prod key only prod's.

**Secrets in each namespace**, all created by Bedag's operator (`<stage>` =
`test` / `prod`):

| Secret | Keys | What |
|---|---|---|
| `aw3-pgr-atlas-s3-<stage>-s3-admin-keypair` | `accessKey`, `secretKey` | tenant-wide S3 key: sees every bucket of the tenant, may change and delete everything. The s3-toolbox uses it |
| `aw3-pgr-atlas-s3-<stage>-admin-credentials` | `username`, `password` | login for StorageGRID's web UI (Tenant Manager), which only Bedag reaches |
| `s3bucket-<bucket>-connection-details` | `AWS_ENDPOINT_URL`, `AWS_REGION`, `S3_BUCKET`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | one bucket's endpoint and key; can't list buckets. It is the same key as the bucket's admin key below, so nothing uses it: the app's `bedag` S3 target reads with `s3-pgr-atlas-ro` instead |
| `s3bucket-<bucket>-s3-admin-keypair` | `accessKey`, `secretKey` | the bucket's admin key |
| `s3-pgr-atlas-ro`, `s3-pgr-datatransfer-rw` | the same five as the connection details | narrower keys for the stage's bucket `aw3-pgr-atlas-<stage>`, one per `S3Access` in the stage's `pgr-atlas/s3/` folder. Checked in the test toolbox: the read-only key lists and reads, and is refused on writes and deletes; the read-write key lists, reads and writes (overwrites too), and is refused on deletes. The app's `bedag` target reads with the read-only key (mapped to `PGR_ATLAS_S3_BEDAG_*` in the stage `values.yaml`). The toolbox has both as the remotes `bedag_ro` and `bedag_rw` |
| `s3-pgr-atlas-archive-ro`, `s3-pgr-datatransfer-archive-rw` | the same five as the connection details | the same pair for the archive bucket `aw3-pgr-atlas-<stage>-archive`, with the same two policies. Checked in the test toolbox, reads only: both keys list the archive bucket; writes and deletes are untried. An `S3Access` belongs to one bucket, so the archive bucket has its own keys. The toolbox has them as the remotes `bedag_archive_ro` and `bedag_archive_rw` |

None of these secrets are in Git. `kubectl get secret … -o yaml` shows them
base64-encoded; treat the output as a password.

**Rotation:** Bedag issues all of these keys and the Tenant Manager
passwords, on both stages. Managing and rotating them is Bedag's
responsibility; the maintainers have no control over them.

**Network:** a pod reaches the grid only if a CiliumNetworkPolicy allows
`x7ba-s3-kakbfe.infra.be.ch:10443` for it: `allow-egress-s3` for the app pods,
`allow-egress-s3-toolbox` for the toolbox. DNS and the proxy (Hosttech) are
allowed cluster-wide; only the toolbox is configured to use the proxy.

## 3. Working with the buckets: s3-toolbox and s3m

Bedag's S3 can't be reached from outside its clusters, so every stage runs an idle pod,
**`s3-toolbox`**, with `s3m`, `rclone` and the AWS CLI, and with the tenant admin
key and a Hosttech key already set (the toolbox's own Secret
`s3-toolbox-hosttech`, SOPS-encrypted in `deploy/stages/<stage>/s3-toolbox/`). Open a shell in it (Teleport
session, VPN):

```bash
export KUBECONFIG=~/.kube/bedag.yaml
kubectl --context teleport.ci-bedag.ch-kb-common-test -n aw3-pgr-atlas-test-apps exec -it deploy/s3-toolbox -- bash
# prod: --context teleport.ci-bedag.ch-kb-common-prod -n aw3-pgr-atlas-prod-apps
```

`s3m` ("S3 manager") knows two remotes, `hosttech` and `bedag_admin`. Paths look like
rclone's: `<remote>:<bucket>/<key or prefix>`.

It has two more, `bedag_ro` and `bedag_rw`: the read-only
and the read-write key for the stage's bucket `aw3-pgr-atlas-<stage>` (section
2). Copy with `bedag_rw` as the target; `bedag_admin`, the tenant admin key, is for
what the narrower keys can't do (deletes, versioning, other buckets). They can't list buckets (`s3m buckets` says so for each); name the
bucket, e.g. `s3m ls bedag_ro:aw3-pgr-atlas-test/`.

The archive bucket `aw3-pgr-atlas-<stage>-archive` has its own pair,
`bedag_archive_ro` and `bedag_archive_rw`. Each pair's keys
belong to its own bucket: on test, `bedag_ro` is refused on the archive bucket
and `bedag_archive_ro` on the main bucket. `bedag_admin`
works on both.

| Task | Command |
|---|---|
| Buckets and their versioning | `s3m buckets` |
| List | `s3m ls bedag_admin:aw3-pgr-atlas-test/some/prefix/` (`-r` for everything below) |
| Objects and size per folder | `s3m du bedag_admin:aw3-pgr-atlas-test/some/prefix/` (current versions only) |
| Versioning status / on / off | `s3m versioning bedag_admin:aw3-pgr-atlas-test [on\|off]` |
| All versions of a file | `s3m versions bedag_admin:aw3-pgr-atlas-test/file.txt` |
| Download (also an old version) | `s3m download bedag_admin:aw3-pgr-atlas-test/file.txt [dest] [--version-id ID]` |
| Delete / bring back | `s3m delete …` (versioned bucket: adds a delete marker) / `s3m undelete …` |
| Make an old version current | `s3m restore bedag_admin:aw3-pgr-atlas-test/file.txt --version-id ID` |
| Copy Hosttech → Bedag | `s3m copy hosttech:adelboden-test bedag_admin:adelboden-test` (dry run), then `--run` |
| Watch / stop copies | `s3m jobs`, `s3m logs <job> -f`, `s3m stop <job>` |
| Anything else rclone / AWS CLI can do | `s3m rclone <args>`, `s3m aws bedag_admin <args>` |

What to know:

- **It asks before changing anything.** For permanent or bucket-wide deletes
  you type the bucket name.
- **Hosttech is read-only for `s3m`.** That is `s3m`'s own guard, not a limit
  of the key: the `rclone`/`aws` pass-throughs don't check it, and the key can
  write and delete (section 6).
- **`s3m copy` is `rclone copy`, never `sync`.** Nothing at the target gets
  deleted, a missing target bucket is an error, and only the current version of
  each file is copied.
- **Large folders are sorted on disk.** `s3m copy` tells rclone to keep at most
  100,000 entries of a folder's listing in memory (`--list-cutoff`). With
  rclone's default of a million, the full copy of `maxi` is killed
  (`OOMKilled`, about 13 minutes into the check phase): `Data-Lake-Silver/` and `locks/` hold over a million
  objects each, on both sides. With the lower cutoff the same copy stayed
  below 400Mi.
- **Copies run in the background** and survive closing the shell. A pod restart
  stops them; start the same `s3m copy` again and it continues where it
  stopped. Merging a change to the toolbox restarts the pod, so check
  `s3m jobs` first.
- **Getting files to your machine:** download into the pod's `/work`, then
  `kubectl cp <pod>:/work/<file> ./<file>`.

Toolbox manifests: `deploy/stages/{test,prod}/s3-toolbox/`. Image and
releases: [tools/s3/README.md](../tools/s3/README.md).

## 4. How buckets are created

**Through Git, as an `S3Bucket`.** Example: prod's bucket
([bucket.yaml](../deploy/stages/prod/pgr-atlas/s3/bucket.yaml)):

```yaml
apiVersion: s3.bedag.ch/v1alpha1
kind: S3Bucket
metadata:
  name: aw3-pgr-atlas-prod
spec:
  bucketName: aw3-pgr-atlas-prod
  s3TenantRef:
    name: aw3-pgr-atlas-s3-prod
```

1. Add the file under `deploy/stages/<stage>/pgr-atlas/s3/` and list it in that
   folder's `kustomization.yaml`.
2. PR, merge. Flux applies it (up to ~10 minutes), and Bedag's operator creates
   the bucket in the stage's tenant plus the Secrets
   `s3bucket-<name>-connection-details` and `s3bucket-<name>-s3-admin-keypair`.
3. Check in the toolbox: `s3m buckets`.

Why not by hand (`s3m rclone mkdir`, `aws s3 mb`, the Tenant Manager): a hand-made
bucket gets no bucket key and no Secret, and nothing records that it exists.
`adelboden-test` on test is such a bucket. Whether the operator takes over an
existing bucket that is later declared in Git is untested; ask Bedag first.

**A bucket with narrower keys** needs three files: the `S3Bucket` and one
`S3Access` per key, each naming the bucket in `s3BucketRef` (it can't be changed
later, and an `S3Access` covers one bucket only). The archive buckets are the
example: [bucket-archive.yaml](../deploy/stages/prod/pgr-atlas/s3/bucket-archive.yaml),
[access-archive-readonly.yaml](../deploy/stages/prod/pgr-atlas/s3/access-archive-readonly.yaml),
[access-archive-readwrite.yaml](../deploy/stages/prod/pgr-atlas/s3/access-archive-readwrite.yaml).
To use the keys in the toolbox, add a remote per key to the stage's
`s3-toolbox/deployment.yaml` (`S3M_REMOTES` and the four `S3M_<NAME>_*`
variables); that restarts the toolbox, so check `s3m jobs` first.

Good to know about `S3Bucket`:

- **No versioning field.** Versioning is switched with `s3m versioning`
  (section 5).
- **Avoid `lifecycleManagement.expirationInDays`.** It deletes *current*
  objects after N days, which is wrong for data. (Cleaning up *old versions* is a
  different kind of rule, which the S3Bucket can't express.)
- Other fields: `bucketPolicies` (e.g. narrower keys), `s3ObjectLock`
  (write-once retention), `consistency`, `region`. Shown by
  `kubectl explain s3buckets.spec --api-version=s3.bedag.ch/v1alpha1 --recursive`.
- **Removing it from Git does not delete the bucket**: Flux runs with
  `prune: false`. The same goes for the S3Tenant.
- The project's cluster role can't read `S3Bucket`/`S3Tenant` objects in the cluster (RBAC). Their
  status holds the endpoint (`status.s3EndpointConfig`); the connection-details
  Secret carries the same information.

## 5. Versioning

- Switched through the S3 API: `s3m versioning bedag_admin:<bucket> on`. Once
  enabled, a bucket can never become unversioned again, only *Suspended*
  (`off`).
- In a versioned bucket, overwriting keeps the old version, and `delete` only
  adds a delete marker. `s3m versions`, `undelete` and `restore` work with that.
- **Old versions count toward the tenant quota.** Copying a whole bucket again
  on top of itself doubles its size. Test's quota is 1000 GiB, and
  `adelboden-test` alone is ~600 GB. No bucket has a rule that deletes old
  versions; one would be set through the S3 API, or by Bedag.

## 6. Hosttech

- Ceph; every bucket reports location `f712`, and the S3 gateway accepts any
  signing region.
- **Bedag and PGR-Atlas have exactly one Hosttech key:** the s3-toolbox's,
  named `pgr-atlas-s3m-toolbox` in Hosttech's UI (Secret `s3-toolbox-hosttech`).
  One key for both stages, test and prod, and no other place uses it. Hosttech can't issue a read-only
  key, so it has full access to Hosttech, `adelboden-test` and `maxi`
  included, and the toolbox can copy any bucket with it.
  The project owner issues and rotates it in Hosttech's UI; how to put a new
  key into the toolbox: `tools/s3/README.md`. The app at Bedag has no
  Hosttech key.
- **Every Hosttech key is account-wide and can write and delete in every
  bucket.** Hosttech can't issue a read-only or per-bucket key. That holds for
  the key in the Bedag stages' toolbox, in developers' `.env`
  files and in the GitHub Actions secrets, so each place gets a key of its own
  instead, which can be withdrawn on its own.
- Versioning is on for `maxi`. A copy to Bedag takes only the current
  versions. `midi`, `mini-teil-a` and `mini-teil-b` are archived at Bedag, not
  at Hosttech.

### The adelboden-test bucket

`adelboden-test` is a copy of the data lake for one region, used for tests
and local development. The Bedag test stage reads its copy in
`aw3-pgr-atlas-test`. The full dataset is in `maxi`.

- **Region:** 464 Kacheln of 1 km², LV95 km e 2598–2619 / n 1135–1156 (the
  Adelboden area plus a 5 km margin).
- **Filter criterion:** an Anriss belongs to the region if its home Kachel
  (`FLOOR(x_anriss/1000)`, `FLOOR(y_anriss/1000)`) is in that range. Anrisse
  from outside whose pixels reach into the region are not included.
- **Built by** a script of the ProBE simulation pipeline, which maintains the
  data lake. Only `Data-Lake-Gold/SIM_SPATIAL/` is partitioned by Kachel and copied by
  prefix. `SIM_ANRISS` and the hulls are batch files and are filtered by
  `id_anriss`.

Sizes:

| Dataset | Size |
|---|---|
| `Data-Lake-Gold/SIM_SPATIAL/` | 290.9 GB (464 Kacheln) |
| `Data-Lake-Gold/SIM_ANRISS/` | about 304 GB (1227 batches; 14.7 % of the campaign's rows) |
| `Data-Lake-Derivate/anriss_umhuellende/` (hulls) | 6.54 GB |
| Overview PMTiles (canton-wide, copied as is) | 7.46 GB |
| **Total, without the regional rasters** | **608.8 GB** |

The derivate rasters (`Data-Lake-Derivate/<metric>/`, e.g. `return_period/`,
`intensity/`) are not in the total.
